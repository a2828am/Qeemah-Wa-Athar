# قيمة وأثر — Qeemah Wa Athar

منصة مجتمعية عربية (RTL) تجمع **البيع والتبادل والتبرّع والمجاني** في سوق واحد، مع **جمعيات خيرية موثّقة** تستلم التبرّعات العينية وتوزّعها على مستفيدين مسجّلين، وتصدر إيصالات استلام موثّقة. المساعد الذكي يعمل محلياً دون أي خدمة خارجية.

- **اللغة والاتجاه:** عربي بالكامل، `dir="rtl"`.
- **الخط التقني:** PHP 8.1+ (بلا أي إطار عمل أو مكتبة Composer)، MySQL/InnoDB في الإنتاج، SQLite للتطوير، CSS/JS مكتوبان يدوياً.
- **الواجهة:** بلا أي اعتماد على CDN — الخطوط أنظمة، الأيقونات SVG مضمّنة، لذا تعمل الصفحات حتى دون اتصال بالإنترنت.

---

## 1) التشغيل على XAMPP (Apache 8080 + MySQL 3306)

هذا هو المسار الذي يخصّك محلياً، ولا يحتاج أي تعديل في ملفات الإعداد:

1. شغّل من لوحة XAMPP: **Apache** ثم **MySQL**.
2. ضع مجلد المشروع داخل `C:\xampp\htdocs\` — باسم `qeemah-platform` (لا يهمّ الاسم فعلياً، لكن هذا هو الرابط المتوقّع).
3. افتح: **`http://localhost:8080/qeemah-platform/install.php`** ← اضغط «تنفيذ التثبيت».
   - المُثبِّت ينشئ قاعدة `qeemah_wa_athar` إن لم تكن موجودة، ويستورد `database.sql` (44 جدولاً + بيانات العرض).
   - يمكن إدخال كلمة مرور MySQL من الصفحة (الافتراضي في XAMPP: `root` بلا كلمة مرور).
4. ابدأ من **`http://localhost:8080/qeemah-platform/`** ودخل بـ `admin@qeemah.test` / `Password123!`.

> **مهم:** لا حاجة لتعديل `config/database.php` ولا `.htaccess` ولا أي مسار. إعدادات XAMPP الافتراضية (`localhost:3306`, `root`, بلا كلمة مرور) هي القيم الافتراضية في `config/database.php`، وروابط المشروع تُحسب تلقائياً من موقع المجلد داخل `htdocs` (تعمل من مجلد فرعي أو من جذر الموقع).
>
> **بعد التأكد من عمل كل شيء على الاستضافة العامة:** احذف `install.php` — فوجوده يتيح لأي زائر إعادة الاستيراد.

### بديلان للتثبيت (بنفس النتيجة)

```bash
# من سطر الأوامر داخل مجلد المشروع
C:\xampp\php\php.exe tools\init_mysql.php

# أو من phpMyAdmin: Import ← database.sql  (الملف ينشئ القاعدة بنفسه)
```

`database.sql` **آمن لإعادة التنفيذ**: الجداول تُنشأ بـ `IF NOT EXISTS`، وبيانات العرض تُضاف فقط إن كانت غائبة — فلا حذف لأي بيانات قائمة.

### استعادة بيانات العرض بعد التجارب

```bash
php tools/init_mysql.php --refresh     # يُفرّغ ما زرعته database.sql ويعيده كما هو
php tools/init_mysql.php --reset       # يحذف القاعدة بالكامل ويعيد بنائها (خطير)
```
ونفس الخيارين متاحان كصناديق اختيار في `install.php`.

### الفحص الآلي على MySQL

```bash
php tools/e2e_test.php http://localhost:8080/qeemah-platform --mysql    # 120 فحصاً
```
الفحص يعيد ضبط بيانات العرض تلقائياً قبل التشغيل، فيمكن تكراره بلا تنظيف يدوي (`--no-reseed` يوقف ذلك).

## 1b) التشغيل للتطوير بلا MySQL (SQLite)

```bash
php tools/build_sqlite.php                      # ينشئ storage/qeemah.sqlite ببيانات العرض
```

ثم `http://localhost:8091`. هذه الطريقة للفحص السريع فقط؛ MySQL هو قاعدة التشغيل الحقيقية.

## 2) النشر على استضافة حقيقية

1. **الملفات:** ارفع مجلد المشروع إلى `public_html` (أو مجلد فرعي — كل الروابط نسبية).
2. **قاعدة البيانات:** أنشئ قاعدة `utf8mb4_unicode_ci` واستورد `database.sql`، أو افتح `install.php` مرة واحدة ثم احذفه.
3. **الإعدادات (اختياري):** بدّل القيم عبر متغيّرات البيئة بدل تعديل الملف:
   ```
   QEEMAH_DB_DRIVER=mysql  QEEMAH_DB_HOST=localhost  QEEMAH_DB_PORT=3306
   QEEMAH_DB_NAME=qeemah_wa_athar  QEEMAH_DB_USER=…  QEEMAH_DB_PASS=…
   ```
4. **الصلاحيات:** `chmod -R 775 storage` (أو امنح المستخدم صلاحية الكتابة).
5. **Apache:** `.htaccess` جاهز (أمان، ضغط، كاش، ترويسات CSP). إن كان الخادم Nginx:
   ```nginx
   try_files $uri $uri/ /index.php?$query_string;
   location ~ /(config|includes|storage)/ { deny all; }
   location ~ \.(sql|sqlite|log|md)$ { deny all; }
   ```
6. **الفحص النهائي:** `php tools/install_check.php` ثم `php tools/e2e_test.php https://example.com --mysql`.
7. **قبل الإطلاق:** احذف `install.php`، وانقل `database.sql` و`storage/` خارج الويب إن أمكن، وغيّر كلمات مرور الحسابات التجريبية.

## 2b) إنشاء حساب جديد (فرد / متجر / جمعية)

صفحة `register.php` تعرض ثلاثة أنواع، وكل نوع يسجّل بياناته الخاصة:

| النوع | ما يُنشأ مع الحساب | الحالة الابتدائية |
|---|---|---|
| **فرد** | دور `user` | نشط فوراً |
| **متجر** | دور `store` | نشط فوراً |
| **جمعية** | سجل جمعية + دور `association_representative` + طلب توثيق للإدارة | `pending` حتى توثّقها الإدارة |

حساب الجمعية **يدخل مباشرة** إلى لوحة الجمعية ويستطيع تجهيز الحملات، لكن استلام التبرّعات
لا يُفعّل إلا بعد التوثيق من **الإدارة ← الجمعيات ← توثيق**. لتصفّح الصفحة كما سجّلتها:

![أنواع الحساب الثلاثة](docs/signup-three-types.png)

### سيناريو حسابين على جهازين (كمبيوتر + هاتف)

هذا هو المسار الكامل المطلوب: كل حساب يبيع ويشتري ويتحدث ويتفق ويستلم.

1. **الكمبيوتر:** افتح `register.php` ← «فرد» ← سجّل («سالم») ← «أضف منتج» ← انشر المنتج.
2. **الهاتف:** افتح نفس الرابط ← «متجر» أو «فرد» ← سجّل («نجاة»).
3. **الهاتف:** افتح صفحة المنتج ← «أرسل طلباً» ← اكتب رسالتك ← «إرسال الطلب».
4. **الكمبيوتر:** «طلباتي» ← `طلبك` ← «قبول الطلب» (تُفتح المحادثة تلقائياً، وتصبح الحالة **جاري الاتفاق**).
5. **الطرفان:** «المحادثات» ← تبادلا الرسائل؛ وفي أعلى المحادثة **شريط تقدم المنتج** وأزرار الحالة.
6. **الطرفان:** زر **«تم الاتفاق»** داخل المحادثة ← يلزم **تأكيد الطرفين** معاً («أكّدت — بانتظار الطرف الآخر»).
7. **بعد اتفاق الطرفين:** زر **«بدء التسليم»** ← ثم زر **«تم التسليم»** يؤكده كل طرف ← الحالة `تم التسليم`.

لا تُكمَل أي خطوة بتأكيد طرف واحد، وكل خطوة تُكتب في سجل غير قابل للتعديل.
يمكن إعادة هذا السيناريو آلياً:

```bash
node tools/two_device_demo.js     # يفتح متصفحين (1366 و390) وينفّذ الخطوات السبع
```

### شريط التقدم وأزرار الحالة

**شريط التقدم لكل منتج:** ست خطوات (إرسال الطلب ← قبول ← الاتفاق ← تم الاتفاق ← التسليم ← تم التسليم)،
كل خطوة منها تحمل **ختم وقتها الحقيقي** من السجل. يظهر في:

- **صفحة الطلب** `request.php` بالتفصيل الكامل.
- **داخل المحادثة** أعلى الرسائل، مع صورة المنتج ورقمه.
- **تحت كل منتج** في «طلباتي ← منتجاتي» إن كانت له صفقة جارية (اضغطه يفتح الطلب).
- **«عمليات جارية»** في لوحة الطالب/البائع.

**الأزرار الثلاثة داخل المحادثة** — في مكان التفاوض نفسه، لا في صفحة منفصلة:

| الزر | متى يظهر | ما يفعله |
|---|---|---|
| **تم الاتفاق** | بعد القبول وقبل تأكيد الطرفين | يسجّل تأكيدك للاتفاق؛ ويبقى «بانتظار تأكيد فلان» حتى يؤكد الطرف الآخر |
| **بدء التسليم** | بعد اكتمال اتفاق **الطرفين** | يفتح مرحلة التسليم |
| **تم التسليم** | في مرحلة التسليم | يؤكد استلامك/تسليمك؛ وتُعلن العملية منتهية بعد تأكيد الطرفين |

وضع «جاري الاتفاق» يظهر كوسم بجانب الأزرار ما دام التفاوض لم يكتمل. لا زر يُنهي العملية بنقرة واحدة —
**تأكيد الطرفين قاعدة محفوظة**، والأزرار تعرض دائماً: «لم تؤكد» أو «أكّدت — بانتظار فلان».

![أزرار الحالة داخل المحادثة](docs/chat-deal-actions.png)

### المحادثة لا تُفتح إلا بعد قبول الطلب

هذه قاعدة مفروضة في الخادم، لا مجرد نص في الواجهة:

- **حُذف زر «تواصل مع المالك»** من صفحة المنتج ومن بطاقة صاحب المنتج — كان يفتح محادثة فورية قبل أي طلب.
- `ChatRepo::openForRequest()` هو المسار **الوحيد** لإنشاء محادثة، ويُستدعى من `RequestFlowRepo::accept()` فقط.
- طلب قديم أو رابط محفوظ يحاول `action=contact` يُوجَّه برسالة: «المحادثة تُفتح بعد قبول صاحب المنتج لطلبك».
- صفحة «المحادثات» الفارغة تقول الصواب بدل ادّعاء محادثة فورية.

النتيجة: لا يمكن مراسلة أي بائع قبل أن يقبل طلباً حقيقياً — لا رسائل عشوائية ولا محادثات بلا طلب.

## 3b) المسار الإلزامي للطلب (طلب ← محادثة ← اتفاق ← تسليم)

كل تعامل على المنصة (بيع، مقايضة، تبرّع، مجاني) يمر بالمسار نفسه، وحالته محفوظة في عمود واحد `user_requests.status`:

| # | الحالة | المعنى | من يفعله |
|---|---|---|---|
| 1 | `awaiting_owner` | تم إرسال الطلب — لا توجد محادثة بعد | مقدّم الطلب |
| 2 | `accepted` | قُبل الطلب وفُتحت المحادثة وحُجز المنتج | صاحب المنتج (أو ممثل الجمعية للتبرّع الموجّه) |
| 3 | `negotiating` | **جاري الاتفاق** — تُكتب فوراً بعد القبول | الطرفان داخل المحادثة |
| 4 | `agreed` | تم الاتفاق — بتأكيد **الطرفين** | الطرفان |
| 5 | `delivery_pending` | بانتظار تأكيد التسليم/الاستلام | الطرفان |
| 6 | `delivered` | تم التسليم — بتأكيد **الطرفين** | النظام |
| — | `rejected` / `cancelled` / `disputed` | حالات مغلقة مستقلة | صاحب المنتج / أي طرف / أي طرف |

**قواعد مفروضة في الخادم (لا في الواجهة):**

- **لا محادثة قبل القبول.** لا يُنشأ أي سجل في `conversations` إلا داخل `RequestFlowRepo::accept()`؛ وروابط `chat.php?with=USER` القديمة تُحوَّل إلى الطلب بدل فتح محادثة جديدة.
- **الطرفان فقط (+ إداري مصرَّح).** كل قراءة أو إرسال يتحقق عبر `RequestFlowRepo::canView()` / `ChatRepo::isParticipant()` قبل الاستعلام، وتعديل رقم الطلب في الرابط يعطي 404 لا محتوى. الإداري يفتح المحادثة للتحقيق فقط عبر `chat.php?c=ID&audit=1`، وكل فتح يُقيَّد في `admin_audit_logs`.
- **تأكيد مزدوج.** لا يصبح الاتفاق «تم» إلا بعد تأكيد الطرفين (`request_agreements`)، ولا يُعلن التسليم إلا بعد تأكيد الطرفين (`request_deliveries`). تأكيد طرف واحد يرسل تذكيراً للآخر فقط.
- **معاملات ذرّية.** القبول (حجز المنتج + فتح المحادثة + رفض الطلبات المنافسة) وتسجيل التسليم (إغلاق الطلب + إكمال المنتج + تبرّع مستلَم) يحدثان داخل `Database::transaction()` فلا يمكن أن تتصارع عمليتان.
- **سجل غير قابل للتعديل.** كل انتقال يُوضَع في `request_status_history` (من/إلى/الفاعل/الوقت/السبب)، ولا واجهة تحذف أو تعدّل صفاً فيه.
- **الخلاف يوقف الإكمال.** `disputed` يوقف كل الإجراءات، يفتح بلاغاً في `reports`، ويُشعر الطرفين والإدارة؛ ولا يعيدها لمسارها إلا قرار إداري مسجّل.
- **التبرّع.** التبرّع الموجّه مرتبط بجمعية محددة (`products.target_association_id` → `user_requests.association_id`), وممثل الجمعية — لا صاحب المنتج — هو الطرف الثاني في الاتفاق والتسليم. التبرّع العام يظهر للجمعيات الموثّقة، وأول جمعية تربطه تصبح المستلمة، ثم يُوزَّع على المستفيد بلا كشف بياناته.
- **إشعار في كل حدث** يحمل رابطاً مباشراً إلى `request.php?id=` أو إلى المحادثة.

**الصفحات المعنية:** `request.php` (غرفة الصفقة: شريط التقدم، صندوق الاتفاق، بطاقات التأكيد، السجل، الخلاف)، `my_requests.php` (شريط تقدم لكل طلب + قبول/رفض مباشر + «عمليات جارية»)، `product_details.php` (شريط الصفقة الحيّة)، `chat.php` (شريط الصفقة + إغلاق للقراءة فقط)، `admin/requests.php` (لوحة الإشراف الكاملة).

## 4) خريطة الصفحات

**الجمهور**
- `index.php` — الواجهة: بحث فوري، تصنيفات، شبكة منتجات، حملات، شرح آلية العمل.
- `product_details.php` — معرض صور، مواصفات، بطاقة المالك، لوحة المساعد الذكي، نموذج الطلب (بيع/تبادل/تبرّع/مجاني)، توصيات.
- `campaign.php?slug=…` — صفحة حملة عامة قابلة للمشاركة (تقدّم، احتياجات، آخر التبرّعات).
- `charity_campaigns.php` — كل الحملات النشطة.
- `assistant.php` — المساعد الآلي: يجيب من بيانات المنصة (مراحل الطلب، الجمعيات، المقايضة، المدن، أرخص المعروض) ويُعلَّم «مساعد آلي».
- `login.php` · `register.php` (5 أنواع مستخدمين) · `sitemap.php` · `robots.txt`.

**المستخدم المسجّل**
- `request.php` — **غرفة الصفقة**: شريط التقدم السداسي، صندوق الاتفاق (ملخص/مكان/موعد)، بطاقات «من أكّد»، سجل الحالة غير القابل للتعديل، الإلغاء والخلاف.
- `my_requests.php` — تبويبات واردة/صادرة، «عمليات جارية» مع شريط تقدم، قبول/رفض مباشر، التقييم بعد التسليم.
- `chat.php` — محادثة فورية (AJAX كل 5 ثوانٍ) بعلامات أُرسلت/وصلت/مقروءة، شريط الصفقة أعلى الخيط، وتُفتح فقط من طلب مقبول وتصبح للقراءة عند إغلاقه.
- `add_product.php` — إضافة/تعديل إعلان، رفع صور، مساعد ذكي للسعر والوصف.
- `favorites.php` · `notifications.php` · `profile.php` (تعديل البيانات، كلمة المرور، حساب الجمعية).

**لوحة الجمعية** (`charity/`, محمية بـ `Gate::requireAssociation()` + صلاحية لكل قسم)
- `dashboard.php` — مؤشرات، تبرّعات جديدة، حملات، أعضاء.
- `campaigns.php` — إنشاء/تفعيل/إغلاق، تفاصيل حملة وبند الاحتياجات.
- `donations_manage.php` — متاح/مستلَم/إيصالات + استلام وتوزيع وإصدار إيصال قابل للطباعة.
- `beneficiaries.php` — سجل مستفيدين خاص + سجل توزيع.
- `members.php` — مصفوفة صلاحيات (حملات/تبرعات/مستفيدين/أعضاء) وإدارة الفريق.

**لوحة الإدارة** (`admin/`, `Gate::requireAdmin()`؛ الأدوار الحسّاسة `requireFullAdmin()`)
- `dashboard.php` — مؤشرات المنصة، رسم 6 أشهر، قِمع التبرّعات، بلاغات، جمعيات معلّقة، آخر التدقيق.
- `users.php` — بحث/تصفية، إيقاف وتفعيل، إدارة الأدوار.
- `associations.php` — توثيق/رفض/تعليق، مع تفعيل حساب الممثّل تلقائياً وإشعاره.
- `products.php` — إزالة/إعادة إعلان مع إشعار المالك.
- `requests.php` — **إشراف على كل العمليات**: تصفية بالحالة وبحث، عدّاد تأكيدات كل طلب، تفتيش المحادثة مسجّل التدقيق، حلّ الخلاف، إلغاء إداري.
- `reports.php` — معالجة/رفض البلاغات + شكاوى المستخدمين.
- `audit_logs.php` — سجل تدقيق للقراءة فقط (من، ماذا، قبل/بعد، IP، الوقت).
- `settings.php` — إعدادات المنصة مجمّعة (عام/حسابات/محادثات/رفع/مساعد ذكي).

## 5) واجهات JSON (`api/`)

كل الواجهات تتحقق من CSRF وتعيد `{ok:true,…}` أو `{ok:false,error:…}`.

| الملف | الغرض | الحماية |

| `request_action.php` | `accept`/`reject`/`cancel`/`agree`/`start_delivery`/`confirm_delivery`/`dispute`/`rate` + `GET ?action=progress` | طرفا الطلب فقط (إداري للقراءة) |

| `fetch_messages.php` · `send_message.php` | رسائل + إيصال قراءة + لقطة من حالة الطلب | طرفا المحادثة فقط؛ الإرسال ممنوع بعد التسليم/الرفض/الإلغاء |
| `toggle_favorite.php` | إضافة/إزالة مفضلة + عدّاد | مسجّل |
| `notifications.php` | جلب/تعليم مقروء | مسجّل |
| `report.php` | الإبلاغ عن منتج/مستخدم/رسالة | مسجّل |
| `assistant.php` | سؤال/جواب المساعد الآلي (FAQ من قاعدة البيانات ثم النموذج إن فُعّل) | عام + CSRF |

| `member_action.php` | إزالة عضو من الجمعية | صلاحية `members` |

## 6) نموذج البيانات

44 جدولاً في `database.sql` تشمل: المستخدمون والأدوار والصلاحيات، المنتجات والصور والتصنيفات، الطلبات والعروض والمقايضات، المحادثات والرسائل وإيصالات القراءة، المفضلة والتقييمات، الجمعيات والأعضاء والحملات وبنودها والمشاركين، التبرّعات والإيصالات، المستفيدين وسجل التوزيع، البلاغات والشكاوى، الإعدادات وسجل التدقيق، والجلسات وسجل الدخول.

- **آلة حالات الطلب (9 حالات):** `awaiting_owner → accepted → negotiating → agreed → delivery_pending → delivered` مع `rejected/cancelled/disputed`؛ والانتقالات مسموحة فقط عبرها `request_transitions()` في `includes/helpers.php`، والقبول يحجز المنتج ويفتح المحادثة، والتسليم يُتمّ الطلب ويُكمل المنتج — كلٌّ في معاملة واحدة.
- **جداول المسار:** `request_status_history` (سجل فقط، لا تعديل)، `request_agreements` و`request_deliveries` (تأكيد كل طرف بوقته)، و`conversations.request_id` يربط كل خيط طلبٍ بطلبه.
- **التبرّعات:** `offered → claimed → received → distributed`، والعام يظهر لكل الجمعيات الموثّقة، والموجّه لجمعية واحدة فقط.
- **الإيصالات:** ترقيم `RCP-YYYY-NNNN` غير قابل للتعديل بعد الإصدار.

## 6b) المساعد الآلي / الشات بوت

**يعمل فوراً بعد التثبيت، بلا مفتاح وبلا إنترنت.** وإذا وُضع مفتاح نموذج، يصبح **النموذج هو من يرد** على الأسئلة الحرة، ويبقى الدليل المكتوب بديلاً عند انقطاع الاتصال.

### أين تجده
- **زر عائم «مساعد»** أسفل كل صفحة عامة (السوق، تفاصيل المنتج، الحملات…) — يفتح لوحة محادثة منزلقة. يظهر للزوّار وللمسجّلين، ولا يظهر داخل لوحة الإدارة أو لوحة الجمعية أو في صفحة المساعد نفسها.
- **صفحة كاملة:** `assistant.php` — محادثة أكبر مع قائمة مواضيع جاهزة.

### من يرد؟ (ترتيب الأولوية)
الرد يمرّ على ثلاث طبقات بالترتيب، وأول طبقة تنجح هي التي تُظهر إجابتها:

| # | الطبقة | متى تُستخدم |
|---|---|---|
| **1** | **النموذج الذكي** | كلما وُجد نموذج مُعدّ: `config/ai.local.php` (محلي، بلا مفتاح) أو مفتاح `QEEMAH_AI_API_KEY` (سحابي) — يرد على أي سؤال حر |
| 2 | **الدليل المكتوب** | إن لم يوجد مفتاح، أو فشل الاتصال/انتهت المهلة/رفض المزوّد — يجيب من `includes/assistant_guides.php` بلا انقطاع |
| 3 | **ردّ صادق** | سؤال خارج المنصة ولم يوجد مفتاح: «لم أجد في بيانات المنصة ما يجيب سؤالك… ولن أخترع إجابة» |

**المرجع الحاسم هو وجود نموذج مُعدّ:** ملف محلي أو مفتاح في البيئة يفعّل النموذج حتى لو كان مفتاح «المحادثة الذكية» في الإعدادات مغلقاً — لأن من يُعدّ نموذجاً يريد استخدامه. احذف الملف أو أزل المفتاح لإيقاف النموذج نهائياً.

### ماذا يجيب الدليل (الطبقة الثانية)
المحرّك يطابق سؤالك على **دليل مكتوب** (`includes/assistant_guides.php`) مأخوذ حرفياً من خطوات المنصة، ثم يضيف **أرقاماً حقيقية من قاعدة البيانات**:

| الموضوع | مثال على السؤال |
|---|---|
| **التبرّع خطوة بخطوة** | «كيف أتبرع بمنتج؟» — يأتي بخمس خطوات + روابط مباشرة |
| الفرق بين التبرّع الموجّه والعام | «ما الفرق بين التبرع الموجه والعام؟» |
| مراحل الطلب والتسليم | «كيف أطلب منتج؟» · «لماذا لا تكتمل العملية؟» |
| المقايضة | «كيف تعمل المقايضة؟» |
| التسجيل (فرد/متجر/جمعية) والتوثيق | «كيف أسجل جمعية؟» |
| الدفع والرسوم | «هل هناك رسوم أو دفع إلكتروني؟» |
| الأمان والإبلاغ | «كيف أضمن أمان المعاملة؟» |
| الحملات والمفضلة والإشعارات والصور والمدن والتصنيفات | أسئلة مباشرة |
| الأسعار والأعداد الحالية | «ما أرخص المنتجات؟» — من قاعدة البيانات |

كل إجابة من الدليل تحمل زرّي تنقّل إلى الصفحة المطلوبة (مثل «أضف منتجاً للتبرّع»)، وكل إجابة تُعلَّم دائماً بأنها **مساعد آلي** مع ذكر مصدرها: «نموذج ذكي» أم «بيانات المنصة».

المطابقة تتجاوز اختلاف الهمزات والتاء المربوطة و«ال» التعريف (فـ«كيف أتبرع» = «كيف أتبرّع»)، وترفض الأسئلة الخارجة عن المنصة بصدق («لم أجد في بيانات المنصة ما يجيب سؤالك… ولن أخترع إجابة»).

### نموذج محلي على جهازك (بلا إنترنت، بلا مفتاح، بلا تكلفة)
نزّل نموذجاً لمرة واحدة، وسيصبح هو من يرد — **ولا يحتاج أي مفتاح**:

```bash
# ويندوز
powershell -ExecutionPolicy Bypass -File tools\local-model.ps1

# ماك / لينكس
bash tools/local-model.sh
```

ثم للتحقق: `php tools/ai_doctor.php`. الدليل الكامل (اختيار النموذج حسب مواصفات جهازك، حلّ المشاكل، وبدائل الخوادم): **[docs/LOCAL-MODEL.md](docs/LOCAL-MODEL.md)**.

باختصار: المنصة تقرأ `config/ai.local.php` (قالب جاهز في `config/ai.local.example.php`) — ملف لا يحوي سرّاً، فيه عنوان الخادم المحلي واسم النموذج فقط.

### ربط نموذج سحابي (اختياري — يتطلّب مفتاحاً)
ضع المتغيّرات في بيئة الخادم فقط:

```bash
export QEEMAH_AI_PROVIDER=openai          # أو compatible لأي مزوّد بشكل /chat/completions
export QEEMAH_AI_API_KEY=sk-...           # السر — لا يُحفظ في قاعدة البيانات
export QEEMAH_AI_MODEL=gpt-4o-mini
export QEEMAH_AI_BASE_URL=https://api.openai.com/v1   # اختياري
export QEEMAH_AI_TIMEOUT=12
```

بعدها يرد النموذج تلقائياً على كل سؤال حر. تحقّق من الحالة من `admin/settings.php` ← **«حالة المساعد الذكي»**: وجود المفتاح، المزوّد والنموذج، آخر ردّ ناجح وزمنه بالمللي ثانية، وآخر فشل اتصال — دون كشف المفتاح نفسه.

**ما يصل إلى النموذج:** رسالة نظام فيها قواعد المنصة + الأرقام العامة الحيّة + عناوين الدليل، ثم آخر ٣ أسئلة من المحادثة. الردّ يتغيّر وسماً في الواجهة إلى «مساعد آلي · نموذج ذكي»، وعند تعذّر الوصول إلى «مساعد آلي · الدليل المحلي (تعذّر الوصول للنموذج)».

**ضمانات لا تتغيّر:**
- بلا مفتاح، أو بمفتاح خاطئ، أو بمزوّد متوقف: الموقع يعمل ويجيب من الدليل — لا شاشة خطأ ولا تعطّل (مُختبر فعلياً بنموذج مزيّف يعمل، ثم بإيقافه أثناء الطلب).
- **حدّ استهلاك:** ١٢ سؤالاً في الدقيقة لكل جلسة، فلا تستطيع تبويبة واحدة أن تستنزف حساب المزوّد.
- **رفض الردّ المعطوب:** إن دخل النموذج المحلي في تكرار لا نهائي، يُرفض ردّه ويجيب الدليل — فلا يرى الزائر حلقة مكرّرة.
- إيقاف `ai_enabled` من الإعدادات **يخفي الزر العائم والصفحة كلياً**.
- يُرسل للنموذج بيانات الإعلانات العامة فقط: لا هواتف، لا عناوين، لا بيانات مستفيدين.
- يُخزَّن سؤال المستخدم فقط في `assistant_threads` ويُحذف بعد المدة (7 أيام افتراضياً).

الإعداد المرجعي بلا أي سر: `config/ai.php`. لا يُطبع المفتاح في أي صفحة ولا في سجلّ الأخطاء.

## 6c) التقييم — من يستطيع تقييم من؟

**أي مستخدم مُسجَّل يستطيع التقييم**، بشرط واحد فقط: **ألا يكون ناشر المنتج**.

| القاعدة | التفصيل |
|---|---|
| **من يقيّم** | أي مستخدم مُسجَّل — سواء شارك في العملية أو لم يشارك |
| **الممنوع الوحيد** | **ناشر المنتج** — لا يقيّم عملية على منتجه هو |
| **متى** | بعد `delivered` فقط (اكتمال التسليم من الطرفين) |
| **كم مرة** | تقييم واحد لكل مستخدم لكل عملية |
| **على من يقع التقييم** | الطرف المقابل: الزائر الغريب يقيّم البائع؛ وفي التبرّع الموجّه يقيّم الجمعية |

### أين يجد المستخدم الزر؟

صفحة الطلب `request.php` محصورة بالأطراف (خصوصية)، لذلك لا تكفي وحدها. أضفنا التقييم في
**صفحة المنتج** `product_details.php`، فكل من يصل للمنتج بعد تسليمه يرى نموذج التقييم مباشرة:

- يظهر تلقائياً عند وجود عملية مُسلَّمة على المنتج لم يقيّمها هذا المستخدم بعد.
- لا يظهر لناشر المنتج، ولا لمن قيّم مسبقاً.

![نموذج التقييم في صفحة المنتج](docs/rating-product-page.png)

### الحالة الحسّاسة: التبرّع الموجّه

يجري الاتفاق بين **المتبرّع** و**ممثل الجمعية المستفيدة**، وقد يكون ناشر المنتج شخصاً آخر.
كان خلل سابق يعتمد `owner_id` مباشرة، فنتج عنه: منع ممثل الجمعية (الطرف الفعلي) من التقييم،
وسماح الناشر (غير الطرف) به — بل والتأكيد على الاتفاق والتسليم.

الإصلاح: صار «من هو الطرف» معرّفاً في مكان واحد، ويستخدمه التقييم وأزرار التأكيد والمحادثة:

- `RequestFlowRepo::expectedParties()` — من هم أطراف العملية.
- `RatingRepo::counterpartyFor()` — على من يقع التقييم.
- `RatingRepo::publisherIdFor()` — من هو الناشر الممنوع.

> **ملاحظة على التأكيدات:** التأكيدات (تم الاتفاق / بدء التسليم / تم التسليم) ما زالت محصورة
> بالطرفين فقط — هذا هو ما يجعل التسليم موثوقاً. التوسيع شمل **التقييم فقط** كما طلبت.

## 6d) الانضمام إلى جمعية — طلب يُقبل لا صلاحية تُمنح

**عند التسجيل كفرد** يمكنه أن يذكر أنه يمثّل جمعية معيّنة. هذا **لا يمنحه أي صلاحية**؛
بل يُنشئ طلباً يصل إلى ممثل الجمعية، ولا تصبح العضوية فعّالة إلا بعد موافقته.

### المسار الكامل

| الخطوة | ما يحدث |
|---|---|
| 1. الفرد يسجّل | يختار الجمعية من قائمة **الجمعيات الموثّقة فقط** + الدور المتوقّع + رسالة اختيارية |
| 2. يُنشأ الطلب | صف في `association_join_requests` بحالة `pending`، ويصل إشعار لممثل الجمعية |
| 3. الحساب يعمل كفرد | يبيع ويشتري ويتبرّع بشكل طبيعي، لكن **بلا أي وصول للوحة الجمعية** |
| 4. الممثل يراجع | `charity/join_requests.php` — يرى الاسم والبريد والمدينة وعمر الحساب وعدد منتجاته ورسالته |
| 5. القرار | **قبول** → يُنشأ صف `association_members` ويُمنح الدور والإشعار · **رفض** → يبقى فرداً ويُبلَّغ بالسبب |

### الفرد يتابع طلبه

صفحة `my_associations.php` تعرض حالة الطلب (قيد المراجعة / مقبول / مرفوض) مع إمكانية **إلغاء الطلب**
والتقدّم لجمعية أخرى. الرابط يظهر في التنقل باسم «جمعياتي» لكل مستخدم غير منتمٍ لجمعية.

![اختيار الجمعية عند التسجيل](docs/register-association-picker.png)

![طلبات الانضمام لدى الجمعية](docs/join-requests.png)

### ما يضمنه التصميم

- **لا صلاحية قبل الموافقة** — الطلب المعلّق لا يُنشئ عضوية ولا يفتح أي صفحة (مُختبَر).
- **لا جمعية إلا موثّقة** — الجمعيات غير الموثّقة لا تظهر ولا تُقبل.
- **طلب واحد معلّق لكل جمعية** — لا تكرار.
- **الموافقة تُنشئ العضوية والدور في معاملة واحدة** — لا حالة وسطى.
- **صلاحية «إدارة الأعضاء» شرط** لرؤية الطلبات أو البتّ فيها.
- ما زال الممثل قادراً على **إضافة عضو مباشرة** ببريده (`charity/members.php`) لمن لا يريد انتظار طلب.

## 6e) أزرار المحادثة — لماذا لا تفتح صفحة JSON

كانت أزرار «تم الاتفاق» و«تم التسليم» داخل المحادثة تُرسَل **إرسالاً عادياً** إلى
`api/request_action.php`، وهو يُعيد JSON فقط. فكان المتصفح يغادر المحادثة ويعرض
نصاً خاماً مثل `{"ok":true,"message":"سُجّل تأكيدك…"}` على صفحة فارغة — يبدو كخطأ برمجي.

**الإصلاح:**

- الأزرار صارت تُرسَل عبر `data-ajax="api/request_action.php"` فلا تغادر المحادثة أبداً.
- `data-done="deal"` يجعل الصفحة تُعاد لتعكس الحالة الجديدة (الزر التالي يظهر مباشرة).
- حماية دائمة في `app.js`: أي نموذج يشير `action=` إلى `api/` يُلتقط تلقائياً حتى لو نُسي `data-ajax`.
- فحصان في الاختبار التكاملي يمنعان عودته: «كل زر في المحادثة يستخدم AJAX»، و«لا نموذج يشير للـ API مباشرة».

![المحادثة بعد الإصلاح](docs/chat-deal-ajax.png)

## 7) الأمان

- PDO مُهيّأ مع Prepared Statements دائماً، وكل المخرجات عبر `e()`.
- CSRF في كل POST، وتدوير معرّف الجلسة عند تسجيل الدخول والخروج، وكعكة `HttpOnly`+`SameSite=Lax`.
- تجزئة كلمات المرور `password_hash` (bcrypt)، وتقييد 6 محاولات/15 دقيقة.
- حماية رفع الصور: فحص نوع MIME الفعلي والحجم، أسماء عشوائية، ومنع تنفيذ PHP داخل `storage/`.
- سجل تدقيق غير قابل للتعديل لأي إجراء إداري، بما فيه فتح الإداري لمحادثة طرفين.
- المحادثة محجوبة خادمياً قبل القبول وبعد إغلاق الطلب، ولا يُكشف وجود طلب أو محادثة لمن ليس طرفاً (404/403 لا نص).
- ترويسات CSP/X-Frame-Options/nosniff في `.htaccess`، وحظر الوصول إلى `database.sql` و`config/` و`storage/`.

## 8) قرارات تصميم

- **المساعد يعمل بلا إنترنت أولاً:** إحصاءات حقيقية من قاعدة البيانات (وسيط أسعار التصنيف، شروط الحالة، الكلمات المفتاحية) ودليل مكتوب كامل — بلا مفتاح وبلا إرسال بيانات المستخدمين خارج الخادم. ومن يريد إجابات حرة يضع مفتاح نموذج في البيئة فيتقدّم النموذج، ويبقى الدليل صمّام الأمان عند الانقطاع.
- **لا مكتبات خارجية:** كل شيء مكتوب يدوياً ليبقى النشر نسخ ملفات فقط.
- **RTL أولاً:** الأنماط مبنية للمنطق العربي (`padding-inline`, `inset-inline-start`)، والأيقونات اتجاهية.

## 9) أدوات

| الأمر | الوظيفة |
|---|---|
| `php tools/init_mysql.php` | ينشئ قاعدة MySQL ويستورد `database.sql` (آمن للتكرار) |
| `php tools/init_mysql.php --refresh` | يعيد بيانات العرض إلى حالتها الأصلية دون مسّ البنية |
| `php tools/init_mysql.php --reset` | يحذف القاعدة ويعيد بناءها من الصفر (خطير) |
| `php tools/build_sqlite.php` | يحوّل `database.sql` إلى SQLite للتطوير السريع |
| `php -l` على أي ملف | فحص الصياغة (كل ملفات المشروع نظيفة) |
| `php tools/install_check.php` | فحص تهيئة الاستضافة (إضافات، صلاحيات، اتصال، جداول، حسابات إدارية) |
| `php tools/ai_doctor.php [--ask "سؤال"]` | يفحص إعداد النموذج: الملف، الخادم، وجود النموذج، ثم يجيب فعلياً |
| `powershell -File tools/local-model.ps1` | يثبّت Ollama وينزّل النموذج ويضبط `config/ai.local.php` (ويندوز) |
| `bash tools/local-model.sh [model]` | نفس العمل لماك ولينكس |
| `php tools/e2e_test.php URL [--mysql]` | 160 فحصاً تكاملياً (دورة الطلب، المحادثة، الجمعيات، الإدارة، المساعد بنمطيه) — يعيد ضبط البيانات قبل كل تشغيل |
